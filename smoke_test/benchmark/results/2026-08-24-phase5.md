# Phase 5 matched topology comparison

These are two matched smoke samples, not a general performance claim.

## Environment and workload

- CPU cores visible: 4
- Ruby: 4.0.6
- Sidekiq: 8.1.7
- Ratomic: 0.4.3
- Redis: Docker `redis:7-alpine`
- Jobs: 2,000 per run
- Work per job: 0.05 seconds
- Checkout timeout: 1 second
- Sidekiq topology: 4 processes × 20 threads × pool size 20
- Native topology: 1 process × 4 Ractors × 20 threads × pool size 20
- Total configured worker/resource capacity: 80

## Results

| Runner | Run 1 | Run 2 | Two-run median |
| --- | ---: | ---: | ---: |
| Ractor-native | 1.523 s / 1,313.61 jobs/s | 1.601 s / 1,249.19 jobs/s | 1.562 s / 1,281.40 jobs/s |
| Four Sidekiq servers | 2.619 s / 763.55 jobs/s | 1.868 s / 1,070.62 jobs/s | 2.244 s / 917.09 jobs/s |

## Interpretation

The native Ractor sample was faster in these two runs, but the measurements
should not be treated as an isolated pooling benchmark. The native runner
performs direct Redis `PING`, `INCR`, and `HSET` operations inside host-owned
Ractors. The Sidekiq runner performs the same worker Redis operations through
real Sidekiq queue polling, job fetch, middleware, acknowledgment, and server
lifecycle behavior.

The result demonstrates that both configurations can process the same workload
with 80 configured workers/resources and explicit Ractor/process topology. It
does not establish that Ractors are intrinsically faster than Sidekiq processes.
Repeat measurements on an otherwise idle host, with the same Ruby, Redis,
Sidekiq, Ratomic, CPU, and workload settings, are required for stronger claims.
